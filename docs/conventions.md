# Conventions

Read this before you change a primitive.

## Layout

```text
contracts/<name>.csil        API and data model of one primitive
lib/rpc, lib/authn           the only shared Go code
primitives/<name>/           one Go module per primitive
  api/                       generated by tools/gen.sh; do not edit
  server/                    service implementation
  store/                     persistence (if the primitive has state)
  cmd/<name>/main.go         the process
  README.md                  purpose, API summary, configuration, tests
primitives/agent/            Python harness (package magi_agent)
primitives/release/          Rust release controller
magi/                        composition layer and human-facing API
clients/python, clients/typescript   generated clients and transports
deploy/                      generic Kubernetes manifests (no private values)
```

Each Go module lists `replace` lines for `lib/rpc` and `lib/authn`
(`=> ../../lib/rpc`), so it builds with `GOWORK=off` in image builds.

Run `tools/gen.sh` after a contract change. It regenerates Go code,
`dispatch.gen.go` server tables, and Python and TypeScript clients.

## Rules

- A primitive imports only its own packages, `lib/rpc`, `lib/authn`, and
  third-party libraries. It never imports another primitive or `magi/`.
- Only `magi/` composes primitives. It uses their generated `api` clients.
- Contract changes are allowed when a primitive needs them. Keep fields
  snake_case. Do not use CSIL unions or bare timestamps; use `uint` Unix
  milliseconds. `from`, `to`, and `service` are reserved words.
- Do not run `git add`, `commit`, `push`, `stash`, `checkout`, `reset`, or
  `clean`. Other agents work in this tree at the same time.
- Do not store private values (hostnames, addresses, accounts, keys) in the
  repository. Use `example.local` names in examples.
- Do not name anything "opal". There is no backwards compatibility.

## Transport and authentication

- `lib/rpc.Server` serves `POST /rpc/{Service}/{op}` with CBOR bodies.
  Register the generated table: `s.Register("ArtifactService", api.ArtifactServiceOps(impl))`.
- Return `rpc.Invalid`, `rpc.NotFound`, `rpc.Denied`, `rpc.Conflict`, or
  `rpc.Unavailable` for client-visible errors. Other errors become 500.
- Every call needs a bearer token (`lib/authn`). `rpc.Caller(ctx)` returns the
  principal. Subjects look like `user:name@domain` or `service:name`.
- Authorization is local to each primitive:
  - A record has an `owner`. By default it is the caller's subject.
  - The caller can read and change its own records.
  - Scope `<primitive>:act-as` lets a service set `owner` or `author` to
    another subject, and act on that subject's records.
  - Scope `<primitive>:admin` permits all operations.
- Configuration comes from flags with environment variable defaults,
  prefixed `MAGI_`. Common settings:
  - `MAGI_LISTEN` (default `:8080`)
  - `MAGI_AUTH_KEYS` (comma-separated issuer key files; public keys are read)
  - `MAGI_DATABASE_URL` (PostgreSQL)
- Serve `/healthz` with `rpc.Mux`. Log with `log/slog` JSON to stdout.

## Storage

- Use PostgreSQL through `github.com/jackc/pgx/v5`. Each primitive has its own
  database. Apply an embedded idempotent schema at startup.
- IDs are random, URL-safe text with a short prefix, such as `art_`, `nod_`,
  `utt_`, `run_`, `env_`.

## Tests

- Unit tests run with `go test ./...` in the module.
- Integration tests use a disposable PostgreSQL. On the development host:
  `MAGI_TEST_DATABASE_URL=postgres://magi:magi-test@127.0.0.1:55432/postgres?sslmode=disable`.
  Create and drop your own database inside the test. Skip when the variable
  is not set.
- Test through the real HTTP transport with a generated client at least once
  per operation. A direct handler test does not find a missing dispatch entry.

## Images

`tools/build-images.sh` builds Go commands with one shared Dockerfile. A
primitive that needs another runtime (Python, Rust, extra tools) has its own
`Dockerfile` that builds from the repository root.

## Documentation

Write in ASD-STE100 Simplified Technical English. Keep README files short:
purpose, API summary, configuration, how to run, how to test, known limits.
